# 斗法领航贡献指南

本文档面向本仓库的代码贡献者，规定提交信息与变更日志的写法以及发布流程。系统结构见[架构文档](./ARCHITECTURE.md)；部署与运维见[部署文档](./DEPLOYMENT.md)。

## 1. 提交信息

### 1.1 标题格式

```
<type>(<scope>): <subject>
```

- **type**：必填，英文小写，取值见第 4 节。
- **scope**：选填，用中文模块名，如 `卡片`、`分类`、`Widget`、`搜索`、`图标`、`壁纸`、`设置`、`认证`、`备份`、`依赖`、`部署`；跨模块改动可省略或用 `全局`。
- **subject**：必填，中文动宾短语，直接描述改动本身，不超过 50 个字符，句末不加句号。中英文与数字混排时，两者之间加一个空格（如「新增 Redis 缓存」）。

不写仅含版本号的标题——版本号由 Git 标签与 Release 承载，不进入日常提交标题。版本提交由 `scripts/release.sh` 自动生成，信息固定为 `chore(release): 发布 vX.Y.Z`，不手动书写。

### 1.2 正文

- 标题与正文之间空一行。
- 正文使用无序列表，**条目数随改动规模而定**：小改动写一条即可，较大改动控制在 2 到 5 条，条目应提供有效信息，避免形式化表述。
- 说明本次改动本身：改了什么、为什么改、影响范围（受影响的模块、接口或部署链路）。
- 不写「来源：……」「修改了代码」这类交代出处或没有信息量的内容。
- 禁止任何自动签名（`Generated with …`、`Co-Authored-By` 等）。

### 1.3 示例

```
fix(搜索): 修复拼音首字母匹配在含数字卡片上失效

- 匹配前统一把数字与字母之间的分隔符去掉
- 影响卡片搜索与 Cmd+K 面板，不涉及接口变更
```

## 2. 变更日志

`CHANGELOG.md` 是发布说明的唯一事实源，也是应用内「关于」弹窗的数据来源。

### 2.1 格式

```markdown
## v1.0.0 - 2026-09-21

版本简介：一行散文概述本版重点（可省略）

### 亮点

- 面向使用者的能力描述，3–5 条（应用内只展示这一段）

### 新增

- 卡片支持弹框 iframe 打开，尺寸可拖拽并持久化

### 修复

- 修复壁纸遮罩预览边缘缝隙
```

- **版本标题**：`## vX.Y.Z - YYYY-MM-DD`。`v` 前缀必须保留，日期可省略但建议写出。最新版本放在最上方。
- **版本简介**：版本标题与首个分类之间的散文行，作为该版本的概述（可省略）。
- **「亮点」分类**：面向**使用者**的能力描述，3–5 条，**每个版本必写**。应用的「关于」弹窗与更新提醒只展示它——`### 部署与运维`、`### 开发与质量` 这类面向开发者的分类不会出现在应用内。
- **分类标题**：三级标题，中文。常用 `### 新增`、`### 变更`、`### 修复`、`### 移除`，也允许按功能域分组（如 `### Widget 小组件`）。
- **条目**：以 `- ` 开头的一行描述。

### 2.2 格式不可随意更改

- `scripts/generate-changelog.ts` 在构建期解析该文件并生成 `src/lib/changelog.generated.json`，供「关于」弹窗展示。**标题行不符合上述格式时会被解析器跳过，其下条目并入上一版本段落**（出现在首个版本之前的内容则被整体丢弃），应用内更新日志会因此缺失或串段——例如 `## [0.1.3] - 2026-04-25` 这类写法得不到独立版本。
- 应用内只渲染「亮点」（未写时回退版本简介），因此漏写「亮点」会让「关于」页只剩一行简介，其余分类照旧完整出现在 Release 说明与仓库文档中。
- `scripts/release.sh` 会提取当前版本的段落作为 Release 的说明正文。
- 变更日志与应用内展示的唯一校验方式是：改完后执行 `npm run gen:changelog`，确认输出的版本数正确。

### 2.3 版本段落何时补

日常开发按需在顶部新增段落或往当前段落里追加条目；发布时若缺少当前版本段落，`scripts/release.sh` 会依据上一个 tag 以来的提交自动补一段，之后可人工润色。

## 3. 正式版本发布流程

版本号的事实源由 `package.json` 的 `version` 与 `CHANGELOG.md` 共同承载。发布全流程由仓库根目录的 `scripts/release.sh` 统一接管，**严禁手动修改版本号或手动打 Tag**。

### 3.1 版本类型判定（SemVer 规则）

发布前需根据自上个 tag 以来的提交内容明确发版档位：

| 档位 | 适用场景 | 示例 |
|---|---|---|
| `patch` | 缺陷修复、内部重构、样式对齐、工具链/技能等**对用户能力无增减**的变更 | bug 修复、性能微调、react-doctor 清理 |
| `minor` | 新增**用户可见能力**（新 Widget、新设置项、新集成等向下兼容功能） | 新增 qBittorrent widget、新增壁纸功能 |
| `major` | **破坏性变更**（部署方式、配置文件格式、数据库模型不兼容，需用户手动介入） | 移除必要配置、重大架构重构 |
| `X.Y.Z` | 直接指定显式版本号 | 如 `1.2.0` |

> 内部/元功能（构建工具、版本检测器、工具链配置）默认按 `patch` 升档；混合变更按最高档选取。

### 3.2 发布前置准备

1. **工作区状态**：处于 `main` 分支，且工作区干净无未提交改动（`git status` 显示 clean；有日常改动须先按第 1 节完成提交）。
2. **环境凭据**：本地 `.env` 或系统环境变量已就绪：
   - `REPO_TOKEN`：具备目标仓库写权限（用于创建 Release、Git 推送）；
   - `PACKAGE_TOKEN`：具备目标容器镜像库写权限（用于 `docker login` 与推送镜像）；
   - （可选）`CODE_HOST` / `REPO_NAME` / `CONTAINER_REGISTRY`：平台自适应配置（默认连接 `code.idiswy.cn`，亦支持切换至私有 GitHub，详见[部署文档](./DEPLOYMENT.md)第 12 节）。
3. **Docker 引擎状态**：Docker 正在运行（`docker info` 正常返回），且支持 `docker buildx` 多架构构建。
4. **更新日志确认**：可在 `CHANGELOG.md` 顶部预先写好人工润色条目；若未提供，脚本会自动从 Git 提交生成初始段落。

### 3.3 执行发布命令

进入仓库根目录，执行对应档位的发布命令：

```bash
# 发布补丁版本（最常用）
bash scripts/release.sh patch

# 或发布特性版本 / 主版本 / 显式版本号
# bash scripts/release.sh minor
# bash scripts/release.sh major
# bash scripts/release.sh 1.2.0
```

**首次发布**：当 `package.json` 的版本号已经是待发布的版本（如 `1.0.0`）且尚无同名 tag 时，用**显式版本号**调用，脚本会识别为首次发布、跳过升档：

```bash
bash scripts/release.sh 1.0.0
```

此时版本文件通常已与目标一致（`CHANGELOG.md` 段落与 compose 的版本示例都写好了），脚本会跳过版本提交，tag 直接指向当前 HEAD。重复发布会被「tag 已存在」拦下。

> **自动化流水线**：脚本依次执行：凭据校验 → 升级版本号与 compose 示例 → 更新 CHANGELOG 产物 → `npm run check` 与 `typecheck` 质检 → 生产构建 → 生成版本提交（`chore(release): 发布 vX.Y.Z`）与 Git Tag → Docker Buildx 双架构镜像构建推送 → 推送 Git 与 Tag → 调用 API 创建 Release。

### 3.4 异常处理与恢复

流水线如果在中途断开（最常见：Docker 拉取基础镜像或推送时网络超时），按断点位置处理：

- **版本提交之前**（升版本、质检或构建阶段失败）：脚本退出时已自动还原版本相关文件，排除问题后可直接重跑。
- **版本提交与打 tag 之后**：不要直接重跑（会报 `tag 已存在`）。若尚未推送到远端，先删本地 tag（`git tag -d vX.Y.Z`）并撤销版本提交（`git reset --hard HEAD~1`），排除问题后再重跑；若部分步骤已推送，按断点手动补齐缺失步骤（镜像补推或 API 补建 Release），不要重复执行全量脚本。

## 4. type 取值

| type | 场景 |
|---|---|
| `feat` | 新增功能或能力 |
| `fix` | 缺陷修复 |
| `docs` | 文档、注释、规范更新 |
| `style` | 不影响逻辑的格式调整 |
| `refactor` | 不改变功能的代码结构调整 |
| `perf` | 性能优化 |
| `build` | 构建系统、配置或外部依赖变更 |
| `ci` | 持续集成相关配置 |
| `chore` | 其他日常事务 |
| `revert` | 撤销既有提交 |

## 5. 推送

- 本项目主远端为 `origin`（`ssh://git@idiswy.cn/zhdmcourt/douhang.git`）。
- 默认不推送。需要推送时：`git push origin main --tags`。
- **禁止对 `main` 强推。** 确需改写历史（如统一提交信息）时必须经维护者明确同意，并按规范流程同步分支与标签。
