## 1. Git 提交信息规范

提交信息遵循 [Conventional Commits](https://www.conventionalcommits.org/) 规范，采用中英文结合形式：类型使用英文小写，作用域与描述统一使用简体中文。

### 1.1 标题格式

```
<type>(<scope>): <subject>
```

- **type**：必填，英文小写（取值详见第 4 节）；
- **scope**：选填，模块名称使用简体中文，如 `卡片`、`分类`、`Widget`、`搜索`、`图标`、`壁纸`、`设置`、`认证`、`备份`、`依赖`、`部署` 等；跨模块综合改动可省略或使用 `全局`；
- **subject**：必填，中文动宾短语，简明描述改动内容，长度建议控制在 50 个字符以内，句末不加句号。中英文混排时中间保留一个空格（例如：「新增 Redis 缓存」）。

> **版本提交说明**：日常开发提交中不要在标题中包含版本号。正式版本的发布提交由 `scripts/release.sh` 自动化脚本生成，信息固定为 `chore(release): 发布 vX.Y.Z`。

### 1.2 正文规范

- 标题行与正文之间空一行；
- 正文使用无序列表（`- `），条目数量根据改动规模而定（通常 1 至 5 条），说明改动动机、核心变化及受影响的模块范围；
- 提供切实的技术信息，避免「修改了代码」、「修复了bug」等缺乏实质内容的空泛表述；
- 严禁包含任何自动化助手生成的尾缀签名。

### 1.3 提交示例

```
fix(搜索): 修复拼音首字母匹配在包含数字的卡片上失效的问题

- 匹配前统一滤除数字与字母之间的特殊分隔符
- 影响全局搜索与 Cmd+K 面板，不涉及后端数据接口变更
```

## 2. 变更日志规范 (CHANGELOG)

根目录的 [`CHANGELOG.md`](../CHANGELOG.md) 是版本发布说明的唯一事实源，同时也是应用前台「关于」弹窗与更新通知的数据来源。

### 2.1 日志段落格式

```markdown
## v1.0.0 - 2026-09-21

版本简介：简述当前版本的主要目标与背景（可选）

### 亮点

- 面向最终使用者的 3–5 条核心能力描述（应用前台展示该段落）

### 新增

- 卡片支持在模态弹窗 (Iframe) 中打开，并可自由拖拽调整窗口尺寸

### 修复

- 修复深色模式下壁纸磨砂遮罩预览边缘的间隙问题
```

- **版本标题**：必须严格遵循 `## vX.Y.Z - YYYY-MM-DD` 格式。`v` 前缀必须保留；
- **「亮点」分类（必填）**：每个版本**必须提供 `### 亮点` 分类**。应用前台的「关于」弹窗与更新提醒仅渲染该部分内容；面向开发者的技术细节分类（如 `### 部署与运维`、`### 开发与质量`）不会在前台展示；
- **常规分类**：三级标题，推荐使用 `### 新增`、`### 变更`、`### 修复`、`### 移除`，亦可按功能域划分；
- **条目描述**：统一以 `- ` 开头，简明准确。

### 2.2 解析兼容性要求

- 构建流程会通过 `scripts/generate-changelog.ts` 自动提取该文件并编译为 JSON 供前台消费；
- 标题行格式若不合规，将被解析引擎忽略，导致版本信息遗漏或错乱；
- 编辑修改变更日志后，可执行 `npm run gen:changelog` 快速校验解析结果。

## 3. 正式版本发布流程

版本的唯一事实源由 `package.json` 的 `version` 与 `CHANGELOG.md` 共同承载。全流程必须通过自动化脚本 [`scripts/release.sh`](../scripts/release.sh) 执行，**严禁手动修改版本号或手动创建 Git Tag**。

### 3.1 版本号规则（SemVer）

项目版本号采用 `主版本号.次版本号.修订号`（`MAJOR.MINOR.PATCH`）格式，发布前须根据变更性质选择对应的递增档位：

| 档位 | 对应版本位 | 适用场景 | 示例 |
|---|---|---|---|
| `patch` | 修订号 | 缺陷修复、内部重构、样式对齐、工具链升级等**不增减用户可见能力**的变更 | 修复布局抖动、微调颜色、代码清理 |
| `minor` | 次版本号 | **向下兼容的新增用户能力**（新增小组件、新增偏好选项等） | 新增 qBittorrent 组件、新增壁纸库 |
| `major` | 主版本号 | **破坏性架构变更**（部署架构重大变更、配置文件不兼容等） | 核心数据库重构、运行依赖断代升级 |
| `X.Y.Z` | 显式版本号 | 直接指定目标显式版本号 | 如 `1.0.0`（常用于首次发版基线） |

> 内部构建工具、版本检测机制与工程脚本变更，默认按 `patch` 处理；混合变更按最高档位选取。

### 3.2 发布前置准备

1. **工作区状态**：切换至 `main` 分支，且工作区保持干净无未提交变更（`git status` 为 clean）；
2. **环境凭据就绪**（仅需单个细粒度 Token，本地无需镜像推送权限）：
   - `GITHUB_TOKEN`：在 [Fine-grained tokens](https://github.com/settings/personal-access-tokens/new) 中仅勾选 `douhang` 仓库的 `Contents: Read and write` 权限（用于创建 Release 与推送标签）；
   - （说明）：**容器镜像由 GitHub Actions 云端自动构建并交付至 GHCR**，无需在本地配置 `GHCR_TOKEN`，亦无需在本地运行 Docker 引擎；（若需本地直接编译推送，可设置 `BUILD_IMAGE_LOCAL=1` 并配置具备 `write:packages` 权限的 `GHCR_TOKEN` 作为后备）；
   - （可选）国内 HamGit 平台参数（`HAMGIT_*`）：若需同步发布至国内 HamGit 平台，可在 `.env` 配置 `HAMGIT_REPO_URL`、`HAMGIT_REPO_TOKEN` 与 `HAMGIT_REGISTRY_TOKEN`。发版后可使用 `npm run image:sync` 高速流转镜像。
3. **变更日志确认**：提前在 `CHANGELOG.md` 顶部整理好当前版本的 `### 亮点` 与变更条目。

### 3.3 执行发布命令

在仓库根目录下执行发布脚本：

```bash
# 发布常规补丁版本（最常用）
bash scripts/release.sh patch

# 或发布特性版本 / 主版本
# bash scripts/release.sh minor
# bash scripts/release.sh major

# （可选）在本地直接进行跨架构容器镜像构建并推送（后备模式）
# BUILD_IMAGE_LOCAL=1 bash scripts/release.sh minor
```

**首次发布**：当 `package.json` 的版本号已是待发布版本且远端尚无同名 Tag 时，使用**显式版本号**调用：
```bash
bash scripts/release.sh 1.0.0
```

> **自动化流水线动作**：凭据校验 → 升级版本号与编排示例 → 重新生成更新日志 JSON → 执行 Biome 与 TypeScript 质检 → 生产构建 → 生成版本提交与 Git Tag → 推送 Git 标签与分支 → 调用 API 创建正式 Release → GitHub Actions 云端自动执行多架构 Docker 构建并发布 GHCR 官方镜像（随后可在本地通过 `npm run image:sync` 同步至私有平台与 Docker Hub）。

### 3.4 异常处理与恢复

若发版脚本因网络中断或外部依赖拉取失败而中止，请按断点位置处理：
- **版本提交生成前**（质检或构建阶段报错）：脚本退出时会自动还原版本变动文件，排查原因后可直接重跑；
- **版本提交生成与打 Tag 后**：请勿直接重跑脚本。若尚未推送到远端，先删除本地标签（`git tag -d vX.Y.Z`）并回退提交（`git reset --hard HEAD~1`），排除问题后再重新执行；若已完成部分推送，请手动针对断点补齐缺失步骤，切勿反复触发全量脚本。

### 3.5 Release 记录维护与多仓同步

若新接入镜像仓库、远端历史 Release 记录存在遗漏，或在修改了 `CHANGELOG.md` 后需要对齐云端发行版说明，可使用全自动一致性工具（以 `CHANGELOG.md` 为唯一事实源）：

```bash
# 检查主仓与镜像仓库的 Release 状态与一致性（只读模式，不发起网络写入）
npm run release:check

# 全量同步：自动补齐缺失版本，并自动对齐更新标题与正文差异，确保多仓完全一致
npm run release:sync

# 仅针对指定单个版本进行检查与同步
npm run release:sync v1.0.0
```

### 3.6 容器镜像多端同步与检查

主版本发布后，官方多架构 Docker 镜像由 GitHub Actions 云端流水线自动构建并交付至 GHCR。如需将镜像同步分发至国内 HamGit 镜像平台或 Docker Hub，可运行独立的同步工具（无需本地重复编译）：

```bash
# 检查各镜像平台 Release 镜像包状态（以主仓远程 Releases 为准；默认查最新，加 full 查全部）
npm run image:check
npm run image:check full

# 高速清单同步：自动将官方 GHCR 产物快速分发至 Docker Hub 与国内 HamGit 镜像库（默认同步最新 Release）
npm run image:sync

# 全量同步所有 Releases 镜像包
npm run image:sync full
```

## 4. 提交类型取值说明 (type)

| type | 说明与场景 |
|---|---|
| `feat` | 新增用户可见功能或能力 |
| `fix` | 修复缺陷或问题 |
| `docs` | 仅涉及文档、注释或使用说明的更新 |
| `style` | 代码格式调整，不影响逻辑运行 |
| `refactor` | 代码重构，既不新增功能也不修复缺陷 |
| `perf` | 性能提升与性能优化 |
| `build` | 构建系统、外部依赖或配置变更 |
| `ci` | 持续集成与发布工作流配置变更 |
| `chore` | 日常维护事务、类型微调、内部小工具更新 |
| `revert` | 撤销既有提交 |

## 5. 平台定位与代码分发规范

| 平台 | 访问属性 | 仓库定位与核心职责 | 版本更新检测 | 容器镜像托管 |
|---|---|---|---|---|
| **GitHub** | **海外公开仓** | 官方海外核心代码仓（`github.com/wangyan/douhang`） | **是**（海外环境默认） | **是**（GHCR，海外默认） |
| **AtomGit** | **国内镜像仓** | 官方国内镜像代码仓（`atomgit.com/wang_yan/douhang`） | **是**（国内开启加速） | **否**（不提供镜像服务） |
| **HamGit** | **国内私有仓** | 官方国内私有备份仓（`hamgit.com/wangyan/douhang`） | **否**（私有仓绝不参与） | **是**（官方国内容器镜像直连源） |

应用前台版本更新检测仅面向 GitHub 与 AtomGit；HamGit 虽对外提供国内容器镜像下载，但作为私有代码仓库，不参与国内用户的代码更新检查。
